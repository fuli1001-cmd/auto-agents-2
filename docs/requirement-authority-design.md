# 正式要求与技术选择的共享权威边界

实施补充（2026-10-25）：本设计先于编码落盘。独立预审与回归进一步限定了迁移和无进展语义，补充如下。当前仍在验证，设计文档不代表全部测试或独立复审已通过。

### 已实施的兼容边界

- 交付复核在稳定候选边界执行；已进入 `reintegrating` 或 `repairing_runtime` 的受控工作先沿原有恢复逻辑完成合并/修复、检查和独立审核，再进入发布门禁。不能用工作开始前的提交摘要拒绝尚未完成的合法工作，也不能跳过稳定候选的来源复核。
- 已激活修订的完成许可不可改写。后来针对同一历史候选的补审拒绝或来源争议记作新的观察和后续路由，保留原完成结果及其摘要，不把过去已发生的激活重写为拒绝。
- 来源纠错对文档和命令使用同一个正式引用视图；命令条款必须完整匹配已核验纠错请求的旧条款，短片段、错误责任方、过期父版本、未映射条款或业务目标变化仍拒绝。检查数量一致不作为等价依据。
- 人读引用不是结构身份：计划中已有的五类可纠错目标沿用 `ContractCorrection` 的 target/task_id/index，并绑定完整值摘要。审核从控制器生成的有限条款来源中选择目标；纠错请求及激活再次核对该目标和摘要。参数包含换行、同一文字对应多个命令或同一命令出现在不同位置时，不能把对 A 的争议用于 B。此表不是新增条件语言或执行权限。
- 未接受候选的来源纠错保留作者反馈、旧新条款审核与普通修订门禁，但不提供修改已接受义务的来源例外。两类来源都先从原审核回执重新核对身份；不能通过改 origin/kind 把候选晋升为正式计划，也不能因候选不是正式计划而拒绝普通重提。
- 共享入口为 `review_authority.py` 的有限模型及确定性验证，`workflow_authority.py` 为 Engine/Store 的适配。`ReviewResult` 保留历史读取格式；新的正式审核使用必填 typed schema，避免在原严格 provider schema 中暴露任意属性字典。
- 外部实际回答单独作为来源：保留问题上下文、原始答案、选项 key/label/value 和版本绑定。只有明确的需求询问及原型反馈入口被纳入；恢复许可、产品批准、模型自动回答都不转为新需求。问题内容不是回答者说过的话。
- 许可在发放和实际消费时都核对来源。任务开始、已分发修复、阶段重入、交付复查共享校验；新 PlanPatch 的合法前后版本转换由已激活 journal 证明，不能依靠模型声称来源未变。
- 旧已完成任务的审核不足时，归档旧记录并复验同一实现，不增加实现轮数。已发布但未结束的交付只补审和复验，保留提交及历史。
- 旧 `implementing` 候选仅在完整前像未变、属于首次实现、没有旧恢复许可、当前正式任务及原完成调用的完整任务匹配时，允许同候选独立补审。检查完成调用和同一 identity 的 presentation；重新准备补丁必须精确复现原批次。保留旧候选、计数和批准。已部分应用但缺原文、调用记录缺失、任务变化、旧修复许可缺来源证明等，不补盖摘要，保留现场请求原输入/授权核对。此版不重建任意部分应用工作区。
- 旧 prepared PlanPatch 只补审原候选。原 cycle/failure/attempt、原 request snapshot、完整任务与路径、动作、来源、独立审核及原 CAS 门槛均需匹配；新增外部答复却没有旧授权的答复绑定时不能迁移。已激活事务只核验原历史并另授后续动作，不再次激活。旧许可和旧审核均不覆写为“当时已满足新协议”。
- 无进展链不因改写条款或再次批准重置。固定比较原始输入、实际外部答案与规范化的检查执行事实；新提交输入/新执行事实可开启另一次评估，但历史不清零。这是保守的有限身份比较，不声称能判断任意语义上的进展。
- 测试中的旧阶段夹具须显式提供原输入和对应 schema 的假审核响应；原错误注入、业务断言、计数和拒绝条件保持。生产代码没有“缺来源就默认批准”的测试兼容开关。

## 2. 非目标与不可变边界

不新增任意候选代码执行、系统桌面自动化、证据收集平台、规则 DSL、通用自然语言解释器、审计保留或新模型配置。不改用户目标/同意，不以检查数量代替断言保留，不由外部助手编写产品。保留全部历史、旧问题、批准和累计次数。技术合同不能创造执行能力或扩大文件权限。未知来源不得默认为用户原话或可忽略建议。源事实和未应用提案继续保持不同权威。

本轮不重新运行前三个 demo、不创建新 demo、不安装新的完整产品环境、不永久清理资料。仅小型归档回放与已有测试，最终恢复原 demo5。

## 4. 共享来源与效力契约

来源由控制器从原件/已接受检查点构造，不能从候选自称的 origin 提升。保持两条独立轴：内容来源与当前效力。

来源包括：提交输入（作者未由 CLI 证明，明确不冒称个人逐字原话）、真实已记录答复、已接受规格解释、责任阶段提出的技术选择、作者/审核建议、执行观察、控制器固定规则。效力包括：候选/建议、正式需求、已采纳技术合同、事实证据、执行许可。拥有真实哈希不能跨效力类别转换。

公共 basis 绑定协议版本、运行/阶段、原始输入与规格、当前正式设计/计划及版本、候选身份、检查/观察身份和适用来源。有限标准 ID 由控制器提供；原件定位与内容身份可核对。相同来源通过公共上下文投影与引用目录提供，不能反复嵌套复制历史形成巨型 prompt。原始输入完整可读，敏感路径过滤不变。

正式规格的需求 ID 是索引，不证明后来的任意方法都来自原话。已有设计批准仅证明那些字节曾被审核；其方法仍属于可修订技术合同。没有记录作者来源时保留 unknown/submitted_input，不补造委托或用户签字。

## 5. 共享审核记录与正式采纳

保留现有候选与 ReviewResult 的历史读取，增加新调用必须提供的公共权威评估。不要把缺字段的旧记录自动补成通过。协议必须覆盖：

1. exact basis/candidate/version binding；正式标准覆盖及实际事实来源。
2. 每个会影响流程的 finding 对应正式标准、原件引文、观察、责任方及 effect。advisory 不能触发拒绝或新增执行条件；缺失依据返回同一审核的有界纠正，不自动批准产品。
3. 派生技术选择与用户明确方法分开。候选作者的选择保存在原候选，独立审核给出明确采纳/拒绝/未确认及原文位置。仅责任阶段接受且控制器激活后才成为当前版本技术合同；审核者不能在 resolution 中创造新的必做方案。
4. 对未知证据义务逐项说明用户结果、造成阻塞的方法、方法来源、实际能力事实、保留义务和合法责任方；真实能力缺口继续阻塞。目录只描述四种证据生产能力，不是假定完整 OS 执行能力清单。
5. 新旧技术选择的对应和保护义务须独立审查，不能只声明等价或保持数量。

允许正常技术选择成为合同，例如选择本地存储、选定工具及对应命令；它不能变成不可修改的用户偏好，也不能授予网络或桌面权限。原用户明确指定的方法或者确属实现目标不可缺少的条件，仍需尊重。引用真实但推理错误无法由代码全判，必须在报告与测试边界中明确。

新的共享模块提供 basis 构造、schema/版本适配、响应校验、回执校验和采纳绑定。PrototypeReview、EvidencePlanReview、EvidencePatchReview、PreviewComparison 保留各自专用约束，通过适配调用同一公共边界；不把所有阶段压成同一个业务审核器。

## 6. 生命周期和事务接入

新鲜返回、ProposalRecovery 的完成缓存、Engine invocation 缓存、DesignDocuments 缓存、任务/最终审核复用、预览比较和交付 pending 均须验证公共回执。新协议缺失或过期时，保留旧自动审核，重新做对应只读审核；不删除已发布交付、不伪造旧通过，也不清除原型人工批准。

每个正式采纳记录同时绑定被采纳制品与独立审核身份。源文件变化、规格改变或计划修订后不得复用旧依据。PlanPatch 将公共回执写入现有 prepared journal 并在激活/恢复中复核，保留原子和单次激活语义。许可仍由 RecoveryPolicy 及原 CAS 事务产生，回执本身不是 permit。

历史旧格式可读，但不能用来给新候选授予新版效力。已交付运行不自动重开。旧 prepared 按其冻结版本处理，不伪造新增字段；如果旧记录在本次改造的已确认不安全消费边界必须重审，应保留 journal 并通过已有拒绝/重审路径处理，不能一边发布一边换合同。

## 7. 来源争议与当前等待恢复

来源争议是通用边界的有限恢复分支：

* 未接受计划自己引入的方法回初始 plan；已接受设计的方法回 design；已接受计划合同走 PlanPatch；规格和原始输入确有歧义回 clarify。
* 每次回送携带原始输入、旧条款、正式来源评估、当前版本、保留义务和原审核，不给作者空白计划。
* 先独立审查争议，再通过原有动作选择/授权。不能让争议提出者给自己的说法盖章，也不能复用 plan_patch 许可跨到 design。
* 真正必要能力缺失维持等待；语义或事实不确定时有限诊断并报告，不自行删除要求。

本次旧等待只在严格核对 reason_code、blocked candidate/review/context、原输入、设计回执、源码和未答问题均一致后，允许新版来源重审进入正常流程。只有新独立结论和合法纠错许可成立，才用现有事务将旧未答问题关联为已被纠错取代，保留审计；不能写入 y 或伪称用户安排了操作者。审核期间问题已答、源码变化或许可不匹配则拒绝重用。

设计回送保留 prototype 阶段及其文件/动作/人工批准；改变 design 及下游合同后，旧相关验收失效并重验，源码和历史原件保留。若纠错真的改变了原型，必须走其既有门禁，不能借本规则保留不匹配批准。

## 8. 无进展、错误和安全边界

现有 RecoveryProgress 只对 diagnose/plan_patch 排除相同事实路径。为来源争议增加有限稳定身份，关联原始争议、保护目标、方法来源与相关事实；设计改写、换调用、候选新哈希或再次批准不独自算新进展。复用现有两次同证据无进展的持久记录/停止方式，保留旧消耗；不改全局预算或模型总时限。

格式/来源身份非法是审核响应错误，返回审核纠正；业务缺陷按原责任任务修复；能力事实缺失维持真实前提；内部不变量错误仍是内部错误。取消/暂停正常传播，不消耗为已完成失败。未知外部文件/候选脚本不能成为正式来源或执行指令。

## 9. 验证矩阵与交付门禁

先固定两份真实归档、哈希和旧分支结果：原型旧 ReviewResult 接受了作者自加条款（当前专用协议已拒绝）；计划现分支把完整方法归用户并产生 HumanIntervention。再实现新共享边界，不用手改真实产品计划制造通过。

定向/组合测试必须覆盖：

* 有效引用但来自作者建议、候选文档自称已批准、遗漏标准、非法 owner、未知/过期来源、伪造回执均不产生 gate 效果。
* 用户真的明确指定物理窗口操作仍阻塞；合法已采纳技术依赖保持约束；代码不能机械判定真实引文的全部语义，受控模型反例与独立审核单独报告。
* coverage/design/plan/任务/最终/无变化/重新集成/测试保护/嵌套 preview 的真实 Engine 调用者，而不只向校验器手喂正确结果。
* 来源纠错回送、旧新保留义务、错误目的地、当前未答问题 CAS、用户在审核中回答、重复激活、prepared 中断恢复、原型批准保留、计数不清零。
* 缓存和旧审核复用不能绕过校验；执行事实不能借审核协议新增权限；最终 PNG/完整 JSON/真实文件往返不削弱。
* 相同争议改写不得无限重试；新增相关事实允许重新评估但不抹历史或用户拒绝。

测试夹具需要显式构造新版有效审核；不能在生产代码对测试/假 provider 开后门，也不能全局静默补造原测试的审核依据。新增测试必须包含在旧通用代码失败的真实消费路径。

先运行关联回归/静态检查，再固定最终源码跑完整 pytest，保留源码前后摘要及精确终态。按完整独立修复阶段本地 Git 提交，不 push。固定最终提交进行独立 gpt-6-astra / max 复审，两项通过后才正常恢复 demo5。全量通过不宣称模型语义永久正确。

## 10. 实施拆分、预期文件与回退

实施分为共享权威契约及全部有限消费接入、来源纠错/等待兼容及生命周期闭环两个有明确依赖的阶段；每阶段定向验证后独立提交，最终统一全量/复审。若逻辑不可独立完整则合并成完整修复，不为提交数量拆成半成品。

预计涉及新的有限 authority 模块、models/prototype_review/evidence_admission、Engine/IssueLedger、DesignDocuments/PreviewEvidence、PlanPatch 的审核和 journal 校验、RecoveryPolicy/Progress、公共上下文与证据目录/提示、相应测试及 docs/design.md。只修改接入必要内容，不顺带格式化或重构无关模块。优先沿用 Store 现有 checkpoints/CAS/归档，避免新表和新 CLI。

回退必须保留所有新旧原件与计数，停止活跃控制器后处理；不得用旧程序解释新版未完成 journal 为已验收。实现在超出上述共享边界的接口/权限/数据结构扩展上遇到必要依赖时，先报告，不扩大到审计保留或工作流重写。

## 11. 全量回归暴露的输入与旧状态兼容边界

第二轮固定源码全量结果为 2,523 通过、25 失败。逐项核对发现：旧的子系统测试绕过 intake 后未保留原始输入、原生 provider 夹具未声明审核角色或返回当前类型，以及旧测试把未登记审核直接用于写入许可。不能通过生产默认来源、默认角色或放开许可解决这些测试失败：合法路径显式建立原始输入和真实控制器审核回执，原来的缺失来源及未登记审核另外保留为拒绝反例。原生结果持久化、清理失败及缓存复用仍须验证只付费调用一次。

其中两个输入边界确实不完整：拥有正式产物的五类审核（coverage、research、design、plan、PlanPatch），以及测试变更保护审核，必须在模型调用前提供相应候选对象，不能调用后再以 `KeyError` 失败。测试变更的真实三个入口提供完整 `ImplementationResult` 对象，其回执仍是被审变更证据，不因此成为产物所有者或写入许可。旧激活 journal 若丢失原提案或原审核，必须受控报告冲突并保留原件，不能伪造补齐或以内部 `KeyError` 退出。校验放在现有公共适配器和恢复入口，不扩展为任意 JSON 或自然语言解释器。

合法的激活后恢复测试改为走真实诊断、计划作者、独立审核及事务激活，再在文档落盘后中断。恢复只接受控制器自己的文档变化，任何额外用户改动仍拒绝；候选、累计次数和已激活版本不得重复消费。历史不完整 journal 的原始案例保留，另覆盖真实 journal 分别丢失审核或提案的拒绝情形。所有夹具适配仍需当前源码全量及固定提交独立复审通过，不能沿用本次失败全量作为通过证据。

定向复验另确认一项实际回归：设计审核因协议或来源变化而失效时，先丢弃旧引用会掩盖已声明审核原件的丢失。普通设计恢复与已接受设计的协议复核共用原件完整性校验，在任何新审核之前验证已有引用、字节长度和原审核内容。原件缺失、损坏或绑定不符必须保留现场并报告冲突；没有原始引用的旧格式记录可以按既有规则重新独立审核，但不得把新审核伪称为旧审核。测试覆盖两入口及四类原件损坏，原有拒绝断言保留。

独立复核要求把 journal 的“存在”判定落实为既有结构合同：原审核必须能由普通、时序、合同或证据审核模型解析且原裁定为通过，原提案必须能由 `PlanPatch` 解析。空字典和拒绝裁定不能冒充合法旧原件；没有新 `authority` 字段但原件完整的旧格式仍可走独立重审，不因此重复激活或增加原任务权限。此处不创造新的历史证明，只验证恢复实际消费的原件。
