## 最小目标与边界

保持保守的审核失效规则及正常任务 DAG。仅对已正式派发、尚未产生任务结果的 repair，允许优先使用已经被接受、仍在当前集成提交祖先链中的依赖实现进行原范围修复。历史实现可作为修复输入，不等于当前检查或审核已经通过。依赖的旧失败/过期状态仍保留，修复提交集成后必须再验证，最终所有任务及集成门禁仍须通过。

不引入新恢复动作、权限、预算或计划依赖边。不依据诊断文字授予执行权；使用原 task_authorized/validate_consumption、task_scopes、expected_tasks、正式来源和计数绑定。一般未实现任务、依赖仍需修代码的任务、不匹配或已消费许可均不能使用此路径。不直接改 Demo5 产品、计划或数据库，不降低 tsc/浏览器/业务断言。

## 实现点

1. 在 Engine._develop 的公共调度入口优先识别可执行的已派发 repair。优先批次限制为一个任务，沿用 _task、保护审核、检查、独立审核和 integrate；普通任务仍由 ready_batch 调度，并要求全部上游祖先已验收；下游修复先集成不允许更后方的首次实现跨过上游证据缺口。
2. 对所有尚未重新验收的依赖，要求 task_state.implementation=accepted；从控制器自己的当前/previous_evidence/authority task-history 槽位寻找真实已接受提交，核验历史独立审核、其正式计划中相同任务合同、当前非计划来源身份、全局环境/执行合同不变、提交存在并已纳入当前集成基线。不能递归采信模型反馈或提案。
3. 仅记录调度依据，不写回“通过”、不重签历史回执。原有消费校验在实际执行点继续生效。缺失/未知/过期依据按原门禁处理，不推测成功。
4. task_baselines 的正常合并后，若原实现已接受、仅证据失败/过期，则重新执行检查；needs_repair 或未接受的拒绝候选仍需正式修复许可。新基线的 hash/祖先/用户改动保护和中断日志不变。
5. 若正常中断发生于任务验收后、集成前，只有原许可结果中的精确 commit/source_hash/evidence 与当前有效独立审核、已接受任务状态完全一致，且已完成结果哈希有效时，才续接该提交的集成。许可已消费不允许再次生成或修复；缺失/过期/失败结果保持阻塞。集成后的再次恢复沿用原幂等机制。
6. 当前现场无需外部迁移状态。保留的 TASK-002 修复许可通过正常恢复消费；旧中断诊断由既有机制恢复。原 TASK-001 失败仍归档且重新检查，不伪造关闭。

# 任务验收与恢复许可结果的原子落盘

固定提交 `24f543caedc69f9345efcae9ba9e869e4182e54e` 的独立复审发现：`Engine._task` 先由 `ReviewEvidence.complete` 提交任务接受状态及审核证据消费，再由 `RecoveryPolicy.task_outcome` 单独写许可结果。若前一事务后进程退出或后一写入失败，接受提交已存在但许可仍 started、tasks 为空。新优先调度误走 execute_dispatched_repair，随后 `_task` 直接返回接受提交，许可结果永久缺失。

独立探针在第二个写入函数入口同步抛出 CancelledError，模拟该持久化窗口。两次写入之间没有 await，不声称普通协作式 asyncio 取消自然发生于此处。复现没有重复生成产品或清零计数；缺陷是缺失结果也能推进集成与交付。

最小处理：

1. 提取现有 `task_outcome` 的更新构造，保持原许可和恢复周期的字段、结果与完成规则；失败写入调用仍使用原公开方法。
2. 成功验收时，将构造的许可/周期更新并入现有 `ReviewEvidence.complete(updates=...)`，与任务接受、task_state 和审核证据消费共用一个 SQLite 事务。不引入新事务或状态机框架。
3. 已有接受提交不能回落执行 repair；优先集成仍必须满足已实现的精确 verified 结果、审核和来源校验。
4. `_task` 复用接受提交时，如记录关联恢复许可却没有该任务的持久结果，按现有 StateConflict 保留现场。旧缺口记录不自动补造结果，正常完整旧记录继续兼容。当前 Demo5 不处于此缺口窗口。

验证：原独立反例保留；新增真实 Engine 在接受任务、状态、许可、周期和消费记录写入时的故障注入，证明事务全回滚或全部完成；恢复后不重复实现、不改累计次数。覆盖旧缺结果的拒绝、正常完成结果、仍待另一任务的部分完成许可，以及原有范围/来源/审核/结果完整性反例。定向、相关、冻结源码全量、独立固定提交复审通过后才恢复 Demo5。

不修改产品、真实运行数据库、批准或权限；不清理历史；不把上一版 2653 全量结果用于新源码。此修复单独签入。

新增故障注入夹具初次错误预期回滚至 needs_repair；既有 Engine 在实现开始时已持久化 in_progress。已改为捕获并比较验收事务前完整 task_state，且仍断言其为 in_progress；生产状态规则不改，缺许可结果/假接受仍拒绝。原失败日志保留。
