# 最终审核到责任任务修复的准入修复

## 证据与根因

2026-10-23 demo4 的 run_9ccfd5e078b74be2 在两个任务和最终九条检查通过后，独立最终审核正确发现导入 name/borrower 错误消息被隐藏，原浏览器断言只验证文本，没有验证可见性。此产品缺陷仍须由 aa2 生成候选、保护审核、执行检查并重新验收。

最终审核构造的 FailureRecord 使用 origin_id=final、task_id 空值。RecoveryPolicy.candidates 只有在 failure.task_id 匹配计划任务时才提供 repair；diagnosis_actions 原样复用该集合。因此尚待归属的最终审核、最终检查和应用浏览器故障无法提出修复已有任务的诊断。实际第二份诊断和自动决策均确认无可执行修复选项并停止，未把重复复验当成修复。累计轮数不是过滤原因；配置中的旧次数上限本就不作为生成验收停止条件。

后续机制已经存在：adjudicate 要求非当前任务修复提供每项 RepairTarget 的既有任务、公开字面路径和控制器事实引用；授权绑定源码、计划、故障和任务范围；RecoveryController 把目标任务改为 needs_repair，后继按原规则复验，保留旧证据、血缘及计数，最终证据失效。缺陷是提案准入目录遗漏这条既有路径，不能据此扩大执行权限。

## 最小变更

1. 仅在有已接受任务计划、origin_id=final 且 task_id 为空、尚未开始发布时，在 diagnosis_actions 中声明可以提出 repair。
2. 该声明没有预选目标，不是 ActionPermit，也不进入决策层可直接批准的 candidates。诊断必须先提交明确任务、逐任务目标和事实证据，通过现有 adjudicate 后，授权层才可接收具体 repair。
3. 不从自由文字猜任务、不把全部任务自动重开、不通过 PlanPatch 间接解锁、不修改累计计数、执行范围、产品断言、检查和独立审核门槛。
4. 旧冻结调用和已有待答授权保持原样。原请求在原绑定通过正式答复后，只授权其既有诊断轮；新的诊断调用看到新目录，原有回执继续复用。没有迁移数据库或重写旧输入。

不新增通用路由层、条件语言、预算机制、权限或恢复动作。已发布交付恢复、无计划及 verification_only 路径不获得此入口；任务内已有修复路径不变。
