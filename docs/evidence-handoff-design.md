# P0：显式历史证据交接与工作流回归

设计基线：`25626335b196c96772fb3a203004693bfe2b493b`，工作区干净；2026-10-22 核实。

## 依据与问题边界

demo2 已完成。本轮不重新运行它，也不改变产品、批准记录、内部模型配置或网络设置。本轮解决的是已发生故障所暴露的调用契约薄弱点，不能把“存在薄弱点”说成已证实当前所有路径仍有故障。

历史证据系列修复涉及不同根因：`5bb5578` 保存的未应用提案、`82eeeea` 已观察但未提交的源码、`20ef754` 普通任务返回但未应用的提案、`2562633` 最终／无变更／重新集成审核漏传计划读取范围。它们共用 SourceHistory → ContextPlanner → 只读材料交接，但来源权威和丢失位置不同。最后一次故障中，Vite/Vitest 原件与哈希存在，诊断有 57 个范围而最终审核范围为 `[]`，因此正文被正确标为 outside_scope；调用方选择不完整才是根因。

当前 `collect(..., scopes=())` 仍允许调用方无意省略范围；任务、恢复诊断、进展判断和计划修订分别推导范围。已有六类消费者测试主要把正确收集结果直接注入 ContextPlanner，不能证明实际 engine／recovery 调用者选择正确。`test_final_history_scope.py` 已覆盖三个真实集成入口，应保留并与有限生命周期测试组合，而非另起通用框架。

## 当前调用图与权威

| 调用入口 | 范围来源 | 绑定和生命周期 |
|---|---|---|
| 任务实现、受保护变更审核、实现审核 | 当前任务 allowed_paths | task revision、execution contract、任务工作区源码；应用后重新收集 |
| 最终审核 | 当前批准计划所有任务范围并集 | 当前计划、集成候选、最终调用输入身份 |
| 无变更审核 | 复用来源计划；确实无计划时仅受保护文件 | 原成功 run 的继承计划与本次新鲜检查 |
| 重新集成审核 | delivery journal 绑定计划；无计划 journal 明确仅受保护文件 | journal、重新集成候选及新鲜检查 |
| 普通恢复诊断、无进展判断 | 当前计划中失败任务；无任务 ID 时整个计划 | 失败身份、当前计划、源码、原累计账本 |
| 限定计划修订作者与审核者 | 当前计划中恢复决定及故障涉及的任务；无目标时全部 | 首次冻结 recovery/patch-context，作者和审核者共享，恢复复用 |
| 交付恢复诊断 | 控制器已提供的交付允许范围 | delivery journal 和恢复策略；不从模型引用扩展 |
| 设计问题核对 | 明确仅受保护公开文件 | 尚无已批准实施计划；不能借候选计划扩大 |

SourceHistory 的三类材料保持原义：Git 快照是指定提交的文件事实，不是测试修改批准；observed_only 是曾观察到的字节，不是已接受基线或完整路径清单；proposal_only 是返回或归档的建议，不证明已经应用、检查成功或新增验收义务。所有材料继续按当前范围重新筛选，保留原始内容身份和来源。

## 最小实现

只修改现有 SourceHistory API 和现有调用方，不增加新服务、材料格式、动态规则或持久化层。

1. `collect(rid, work, scopes)` 移除默认参数。显式空范围仍合法；遗漏参数立即报错，不能悄悄生成缺少正文的材料。它仍作为交付控制器的明确范围入口和底层收集实现。
2. 增加 `collect_protected(rid, work)`，明确表达无计划阶段的只读受保护历史范围。原设计问题核对及确实无计划的兼容分支使用此入口。
3. 增加 `collect_task(rid, work, task)`，直接使用调用方已经绑定的 TaskSpec.allowed_paths，保留原顺序，避免仅 API 整理改变缓存或恢复进展身份。任务实现和两种任务审核使用它。
4. 扩展现有 `collect_plan(rid, work, plan, *, task_ids=None)`。必须显式提供非空的 PlanResult 对象；无任务的合法 verification_only 计划仍可得到受保护范围。None 不能隐式冒充无计划分支。task_ids=None 表示整个计划；显式目标集合必须非空且全部属于该计划，否则在收集前抛 StateConflict。选中任务范围按现有规则 sorted(set(...))。诊断、无进展判断和计划修订共用该选择逻辑。
5. 已有冻结的 patch context 和调用记录不重建、不覆盖；只有首次构造时走新入口。计划来源仍由上表中的调用者确定，收集器不猜“最新计划”，也不宣称能验证任意模型对象是批准计划。

任务入口保留已绑定 TaskSpec 是为了不把写权限或任务版本重新推断交给历史收集器。计划入口只检查确定性的选择一致性；语义完整性仍须独立审核。未知任务目标不回退到整个计划或空范围。

## 兼容性、身份与安全

- 清单保持 v4，内容、过滤、来源与差异算法不变。相同源码、锚点、范围、隐私策略、提案及观察产生原来的记录和哈希。
- 不把新的 API 标签或调用用途加入恢复 basis，也不升级持久化版本。这样不会仅因本轮重构刷新无进展额度、消费新授权或废弃冻结材料。
- 内部 Python 调用者原来省略 scopes 的用法须改成明确入口；不改变 CLI、配置、数据库和产物读取兼容性。所有仓库调用点一次核对；不承诺未公布的外部内部-API 用户仍兼容。
- 读取范围不增加任务写权限。保留敏感路径过滤、UTF-8 普通文件限制、符号链接／子模块拒绝、内容和长度校验、缺失锚点状态；不挂载原生 Git／凭据，也不沿正文中的 hash 任意读取。
- 旧观察中曾选入的文件不能突破新的窄范围；未应用提案不能进入源码事实或验收义务。
- 本轮不更改日志保留／资源回收、Provider、检查器、网络、浏览器或依赖缓存。

## 验证矩阵

| 场景 | 真实路径／验证点 |
|---|---|
| 误省略范围、无计划冒充计划、空目标、未知或部分未知任务 | 收集前拒绝；旧代码能默许的遗漏／None 行为需有红灯复现；不得扩大范围或产生新材料 |
| 全计划与指定任务选择 | 与改动前显式 scopes 的完整记录一致；任务顺序保持；无任务计划、显式无计划保持原受保护选择 |
| 生成 → 受保护候选拒绝 → 修复 → 检查 → 实现审核中断 → 恢复 → 最终审核 | 调用真正 WorkflowEngine，检查未应用提案仍 proposal_only、受保护检查未弱化、已观察源码仍 observed_only、恢复不重复实现或清零次数；在真实调用输入上编译 ContextPlanner 并读取附件正文／差异 |
| 恢复诊断与无进展判断 | 使用真实 RecoveryController/RecoveryProgress 调用，失败任务范围一致；来源身份和计数不因入口整理改变 |
| 计划修订冻结后恢复 | 使用真实修订入口，作者／审核者读同一范围材料，不用测试手工塞入正确 history；过期／未知目标不能静默扩大 |
| 最终／无变更复用／重新集成 | 保留现有三个真实工作流测试；断言相应批准／继承／journal 计划范围、历史原件和挂载正文 |
| 反例 | 非任务文件正文不可读，敏感路径／二进制／链接继续排除；缺失或损坏证据不能视为通过；提案中的引用不能铸造事实；旧冻结记录不变 |

只选以上有现实依据的组合。复用既有测试设施，真实 Git、Store、检查执行和恢复状态机，模型与环境安装用固定测试替身。没有真实付费模型语义判断、远程下载和多机并发的验证，不把这些测试结果外推为“所有工作流已根治”。已有只读 demo2 归档可核对同范围记录身份与两份配置正文，但不得改动交付状态或重跑产品。

先执行新回归对旧实现的失败证据，再执行目标子系统、Ruff、diff 检查及指定 .conda-env 的全量 pytest。全量前后保存受测源码摘要，最终提交前检查相同版本。若测试发现新的跨层根因，先判断与本方案的必要关系；不借 P0 扩大修复范围。

## 验收、失败处理与回退

验收要求：生产调用点全部选择明确入口；有计划的审核不能通过遗漏参数退化到空范围；真实调用者链路能观察正确原件、提案和历史身份；既有门禁、检查和恢复预算行为保持；针对旧代码的红灯、新代码回归、静态与全量均有记录。

失败时保留完整错误和现场，不通过删断言、扩大读取或重写旧记录获得通过。未知目标／缺失计划的 StateConflict 沿既有控制器保护流程处理，不自动生成新的人工授权或无穷重试。若现有合法调用依赖不明确的范围，先核对其授权来源，再选择明确分支。

回退使用本次独立 Git 提交的正常 revert；无需数据库迁移或改写产物。新增测试和文档可一并回退，既有已完成 demo2 保持原状。恢复工具链预检、最小审计包、共享依赖缓存列为后续独立议题，本轮不实施。
