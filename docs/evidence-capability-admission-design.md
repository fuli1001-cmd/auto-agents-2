# 有限证据义务准入与跨阶段验证设计

设计基线：2026-10-23，`b7b2776512823aee2b789bdc2c0693d030a8c4d2`，LAPTOP-UE3M8TAU / Ubuntu-20.04，工作区干净。实现和测试使用仓库 `.conda-env`。本方案依据 demo3 复盘及当前源码；不重新执行已交付 demo。

## 1. 已证实问题与目标

demo3 revision 4 把产品锁文件编辑交给环境准备器，并要求该组件提供未采集的有效求解配置。独立审核曾批准这些派生条款。`b7b2776` 已保存真实 `capture_scope`，并帮助正式修订恢复运行，但 `TaskSpec.acceptance` 和初始计划准入没有把证据义务与现有生产能力建立确定性联系。

当前链路是 `WorkflowEngine._pipeline` → `validate_plan` / 命令校验 → 独立 plan review → 保存计划；修订是 `RecoveryController._patch` → `apply_patch` → 独立 review → prepared → `Store.activate_plan_patch`。后者已有作者/审核分别冻结的 v3 contract journal，以及旧 v2 的有证据兼容读取，不能再把两种角色的来源合并。纯 Node 环境工具缺口已由 `64ffde5` 修复；本轮增加跨阶段验证，不重新设计安装器。

TASK-002 的内存附件没有成为控制器可采集的所需文件。现有收集器并非已确认错误；需要提前说明真实落盘协议，并用实际 Playwright 输出与 VerificationService 验证。

目标是提前阻止**已声明的、有限证据类型**使用不存在的能力、错误生产者、错误时点或过期版本，同时让独立审核明确检查漏映射与来源。代码不识别所有自然语言，也不能证明任意条款语义等价。

## 2. 非目标

- 不引入通用条件 DSL、插件化规则引擎、任意流程回退或全工作流重写。
- 不新增有效 solver 配置采集器，不读取宿主私有配置，不改代理、TLS、凭据、模型或权限。
- 不实现审计保留，不清除原件，不修改三个 demo 的源码、Git、数据库或交付状态。
- 不把能力登记当作安装成功、版本可获得、附件已生成或验收通过；不减少断言、检查、用例下限。
- 不为验证重新安装完整 demo 或创建 demo4，不用缓存命中要求强制产品版本迁移。

## 3. 有限能力目录

由控制器代码维护一个不可由模型扩展的目录。每项包含能力 ID、协议版本、实际责任组件、产生阶段、支持的观察范围与明确不支持项；目录内容计算摘要。

| 类型 | 生产者和阶段 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 已安装依赖快照 | EnvironmentManager，环境准备后采集 | 记录中的运行时、已安装包身份/依赖边和实际安装来源状态 | 完整求解时配置、任意兼容性证明、未来安装保证 |
| 完整依赖锁 | EnvironmentManager，环境准备后采集 | 已记录锁的内容及身份、所选输入/环境绑定 | 未记录的全局 pins、channel 优先级或自动改写产品锁 |
| 产品浏览器身份 | 现有 Node/浏览器运行组件，环境准备/验证 | 当前驱动、实际浏览器制品与使用绑定 | 用控制器原型浏览器冒充产品浏览器、不同版本互换 |
| 测试文件附件 | VerificationService，检查执行/采集 | 实际采集文件原件、内容身份与来源 | 仅内存 body、文件名、附件计数或 complete 标签替代所需内容 |

精确 ID 和组件名以实现中的现有生产调用为准，测试绑定实际记录与目录声明。目录只是协议，引用它不能铸造项目事实。条件采集和 `not_recorded`/`not_collected` 必须继续如实保留。

## 4. 结构化义务与来源

新计划增加可版本化的证据合同；存储层仍可读取未含该字段的旧 PlanResult。合同包含模式版本、能力目录摘要、当前原需求/规格的来源绑定，以及有限义务列表。

每项义务绑定一个确切的任务验收条款或有限检查字段（任务 checks、final_checks、runtime_prepare、runtime_probes）的目标/索引和完整原值；包含稳定义务 ID、来源类别（用户要求或模型派生）、关联需求 ID、能力 ID/版本、生产者、产生阶段和所需阶段。允许同一条款有不同证据义务，但禁止重复身份或相互矛盾的绑定。

普通业务断言仍由现有验收和可执行检查承担，不把它们改造成规则语言。作者必须列出所有涉及上述控制器证据的义务；不能通过空列表表达“用户不再要求”。独立审核必须显式判断映射是否完整、来源是否准确、目录能力是否足以兑现原条款。遗漏自然语言映射仍有模型语义风险，文档和结果必须承认这一边界。

来源绑定来自控制器保存的原始输入身份和当前澄清规格，而非候选自己声明的任意 hash。需求 ID 必须真实存在；模型派生标记不赋予删除用户目标的权限。跨阶段修订仍保留原始输入、旧计划、失败、计数和明确条款映射。

## 5. 初始计划与 PlanPatch 的共同准入

共同校验器负责：模式版本、完整目标/原值、唯一性、需求来源绑定、能力目录/版本、生产者、产生/消费时序。未知 ID、版本漂移和未支持能力不能通过；结构错误不进入生效步骤。

独立语义审核负责：真实用户约束与派生选择的区分、漏映射、文字要求是否超出能力范围，以及修订前后实质义务。审核结果需绑定完整候选与目录，不接受一句笼统“等价”。仅审核批准仍不代表安装和检查完成。

初始计划作者和审核者获得同一当前目录及原需求绑定。新生成计划必须给出新合同；无控制器证据义务时也需显式的空合同与完整性审核。未接受候选的结构错误沿现有 plan 重入处理并保留失败材料。

新 PlanPatch 必须给出完整候选的证据合同。普通修订不能悄悄移除旧义务或改掉旧用户来源。已批准错误技术条款仍通过现有 `contract_corrections` 映射/独立审核；无关业务条款、完整命令和用例门槛继续原规则。证据合同变化纳入保守失效，不能把只改元数据当作旧验收仍有效。

## 6. 未支持、未知与真实用户要求

未支持或未知能力始终阻止计划接受/激活。模型派生错误交回计划责任阶段纠正；已接受条款使用正式限定修订，不能直接删数据库条款。

若候选声称这是用户明确要求，该标记本身不成为用户授权或最终事实。使用原始需求、结构化需求 ID 和独立来源判定区分误归因与真实缺能力；已确认的用户必要义务必须保留，沿现有人工前提流程报告具体缺口。回答“重新核对”只重新检验真实能力，不能越过校验或视作取消要求。未知归因不能被解释成“模型派生所以可删”。不新增批准任意忽略证据的选项。

同一事实下反复被拒继续使用现有恢复/无进展出口，不清累计次数、不设置新的任意模型总超时。明确缺能力的候选不能靠反复调用原采集器生成不存在的事实。

## 7. 冻结、激活与兼容

准入记录单独版本化，绑定旧计划、完整候选/patch、来源身份、目录及独立审核；其职责与现有 contract/timing journal 各自明确，不替代它们。prepared 激活事务内重算确定性校验和绑定；篡改、缺失审核、来源或目录过期拒绝，旧计划/计数保持。已激活记录幂等返回。

已有合同修订的作者与审核来源继续按各自冻结上下文验证。新的有限能力来源只使用明确登记的来源字段，不从未保存的当前文件猜补历史。新增字段在旧记录缺失时序列化为原有形状，避免仅新增默认 null 改变旧 PlanResult/hash 或旧 prepared 候选比较。

旧已批准计划可继续按原合同读取和执行，明确视为旧格式，不能冒充已通过新准入。旧 prepared 日志仍按已有严格机制恢复；不补写假的新审核。尚未接受的新候选缺少新字段时，通过既有正式重入重新生成并保留旧候选。旧计划的新修订在新候选中建立合同，不回写历史版本。未支持的新格式不能降级成旧格式绕过准入。

回退无需改写历史 demo 或数据库模式；新合同/准入记录须由支持该版本的控制器处理，旧二进制不能被当作通用恢复办法。源码回退前应保留新日志，明确其恢复边界。

## 8. 提前说明与附件协议

设计、规划、修订、实现和相关审核复用同一能力说明；只有控制器实际可核验的信息才表示为观察事实，宿主 Node、provider Node 和未来产品 Node 不混同。不为“提前说明”盲装依赖或探测未选择渠道。

明确产品锁文件由任务作者提出、保护审核后应用；EnvironmentManager 消费冻结锁并产生环境事实。

Playwright 必要 PNG/JSON 等证据应写到 `testInfo.outputPath(...)`，再用 `testInfo.attach(..., {path, contentType})` 关联。控制器会设置自己的输出目录/报告参数；不要把私有数据或凭据写为附件。内存 body 可以供 runner 使用，但不能据此声称控制器已经保存所需原件。检查结果的完整性字段只说明采集过程状态，语义内容仍须独立审核。

## 10. 验证矩阵

1. 原始反例：小型隔离回放 demo3 revision 4/5 的有效求解配置条款，保持原六检查和业务条件；旧实现接受结构但无能力准入，新实现拒绝不可兑现声明。原文件/数据库保持不变。
2. 机械反例：未知 ID、错误版本/摘要、错生产者/时点、未知需求、陈旧条款、重复 ID、缺失或降级合同；拒绝不得推进阶段。
3. 语义边界：映射不全、用户来源误标、能力不足、隐去必要义务或仅检查数量相同均不能靠批准布尔值生效；使用冻结模型输出验证控制器，不声称证明模型总能判断正确。
4. 真实 Engine 初始 plan 调用：作者上下文 → 校验 → 独立审核 → 正式接受；未支持义务拒绝并保留，真实用户必要能力缺失走明确阻塞，用户要求不被删除。
5. 真实 RecoveryController：旧/新角色不同引用 → 正式纠错 → prepared 中断 → Store 恢复 → 单次激活 → 旧验收失效 → 新鲜检查。坏引用/过期/未审/篡改/重复激活及累计次数不清零。
6. 纯 Node 清单通过现有 EnvironmentManager 工具核验和证据采集，检查实际记录与能力范围一致；缺 Python/pip、明确用户 Python 约束继续原保护。优先复用已有隔离真实安装材料，不再安装完整 demo。
7. 最小 Playwright 测试分别生成内存 body 和 outputPath 文件；通过真实命令包装/采集路径检查 PNG/JSON 原件哈希，不能只断言附件数或 complete。使用已有完全匹配驱动/共享浏览器，不另下载不匹配浏览器。
8. 组合覆盖暂停恢复、无变更复用、最终集成及计划变化后的重新验收；复用现有测试，不做阶段笛卡尔积。
9. 先定向原反例和相邻路径、静态检查，再完整 pytest；保存退出状态、精确数量及源码摘要，源码变化后不得借用旧全量结果。

## 12. 实施核对与兼容性边界

本轮目录实际落在 `evidence_admission.py`，模式版本为 1。四项 ID 分别是
`installed_dependency_snapshot`、`dependency_locks`、`shared_product_browser_identity`、
`test_file_attachments`；前两项与共享浏览器由 EnvironmentManager 负责，附件由 VerificationService
负责。共享浏览器能力随实际共享配置标识可用性；这仍不代表已经安装或实际产生了证据。
`effective_solver_configuration` 明确未采集。`origin=unknown` 不赋予删除权，修订时按用户来源同样保护。

准入事务重验还必须使用现有真实 coverage_checks 的内容摘要、通过状态和源码身份，覆盖普通
verification-only 修订及带 contract_corrections 的修订；不能仅凭新审核元数据使旧覆盖证明继续有效。
该检查复用提取出的 `valid_coverage_receipt`，与原合同校验共享同一事实，未新增一个宽松的证明入口。

提前注入能力目录不能改变已经冻结的诊断输入。新诊断获得当前目录；已完成或被正常取消的旧诊断
保留原上下文，包括原来没有目录的情形。复用旧阶段回执时仅允许缺少这一份已知控制器协议，仍精确
匹配原源码、schema、配置和事实输入；不忽略实际输入漂移。计划准入与 prepared 激活仍独立重验当前
能力和原需求，复用诊断不等于批准计划。计划被拒时继续传递完整 finding、证据和修复要求，不能由
新的结构化拒绝摘要截掉旧的审核意见。

验证采用真实 Engine/RecoveryController 入口和隔离故障注入，而非只手动拼 collector 结果。
demo3 revision 4/5 的只读归档回放保留完整命令和断言，证明旧结构校验能接受未支持的求解配置要求，
新准入不能凭乐观审核布尔值放行。该回放使用冻结的合成审核输出，不冒称真实模型已通过新协议。

不等于 PNG/JSON 原件已归档；outputPath + attach(path) 经真实 VerificationService 保存了相应原件及哈希。

全量验证必须以最后一次完整成功结果及源码摘要为准，失败轮保留。后续版本若改变能力含义或生产契约，
必须更新相应版本/目录身份并补边界测试；不能把旧通过迁移为新版本通过。本轮没有验证付费模型对于
任意自然语言漏映射的识别能力，也没有执行新的完整 demo 或所有操作系统/浏览器组合。
