# 原型审核权威边界：详细设计

日期：2026-10-24；基线 b9885bd。此设计替代早先仅传递能力说明的方案。

## 根因与范围

真实审核 a3471d86… 以 prototype.document 要求完整 #geometry-json 为依据拒绝；f18a8577… 随后要求控制器接入候选 capture-evidence.mjs。原始输入要求最终 PNG、状态 JSON 和真实文件往返，并未授权任意原型采集器。浏览器报告没有采集过该 JSON，不是投影截断。候选脚本从未执行。

当前 Engine._prepare_prototype、_ensure_prototype_approval、recheck_prototype 均使用普通 ReviewResult；模型返回后 _invoke_once 先写 IssueLedger，调用方再依据 approved 触发回退。Finding 没有规范来源，作者材料和正式要求在语义上混用。已有路径权限、六种 BrowserAction、审批和恢复许可继续有效；问题不是任意代码执行。

修复限定上述原型审核共享入口，以及其缓存、问题登记、响应纠正和重检调用。不改变产品业务、计划合同、安装、模型配置或整个工作流；不增加 DOM JSON/下载/文件选择/任意脚本执行；不实现 DSL 或审计保留。最终业务 PNG/JSON/真实文件比较不得取消。

## 正式依据及来源

新增有限 prototype_review 协议，版本独立于实际浏览器检查版本。控制器从 Store/ArtifactStore 构造：

- 当前原型内容及动作身份；当前浏览器观察摘要。
- 捕获的原始用户全文及其不可变 artifact 身份；已确认 clarify 规格和需求 ID/内容摘要。
- 固定原型阶段标准（静态交互、关键/错误状态、响应布局；最终产品实现及文件业务检查属于后续，用户明确时序优先）。
- 由实际 BrowserAction schema 和执行器共享视口生成的有限能力说明。
- 带来源类型和稳定 ID 的可引用标准表。作者 document、EVIDENCE.md、源码和历史审核仅作为材料/线索，不进入标准表。

原始捕获从未存在的旧记录标记 unavailable；缺失不证明某要求可删。存在但损坏的捕获失败关闭。旧规格仍作为已确认来源保留；不能从候选文本补造用户要求。完整文本走已有材料投影，原件不截断。规范来源表与候选材料引用目录分开；引用存在不等于语义成立。

## 审核输出和确定性校验

PrototypeReview 继承现有 ReviewResult，保留可读 summary/findings，但增加：

- basis_hash、candidate_hash，精确绑定来源、阶段协议和观察；
- 每个正式标准的 coverage：satisfied / violated / unverified / later_stage，及解释和实际材料引用；固定原型标准不能 later_stage，用户/规格条款后移必须解释时序且保留后续义务；
- 每个问题的 criterion_id、observation、evidence_refs、kind（defect/evidence_gap/advisory）、owner（prototype/clarify/controller）、requested_capability；resolution 只是建议，不能直接授权动作；
- 来源不明确或声明原型阶段需要尚未支持能力时，必须引用对应原始/规格文字，不能以作者文档作为原要求。

共享验证器检查精确绑定、标准 ID、覆盖完整/唯一、观察引用存在、结论与 coverage/finding 一致、建议不能单独阻止通过、缺证据不得批准、能力和责任组合合法。批准需要所有当前阶段标准满足，不能因拒绝不合法自动批准。代码不证明任意自然语言等价，也不声称合法 ID 能杜绝误读；独立审核仍承担语义判断。

验证发生在 _invoke_once 写 IssueLedger/成功调用回执之前；缓存命中同样验证。非法响应保存原件和具体校验原因，通过已有 ProposalRecovery 仅重新生成同一只读审核响应，保持累计次数、冻结请求和授权。不给产品增加义务，不直接回退原型，不递归创建新的审核系统。

ProposalRecovery 仅为这类可校验响应追加有界、控制器生成的反馈及原件引用；不复制任意异常文本作为指令。一般 provider 格式故障维持原行为。失败无进展仍由现有恢复策略处理，不新增无限自动重试。

## 合法拒绝和责任处理

- 明确 UI/交互缺陷或可由现有原型动作补足的证据：通过既有原型重入修复；回退原因从已验证问题生成，不采用未经约束的自由 summary 作为新条款。
- 真实要求来源/阶段含糊：回既有 clarify 责任阶段，保留原始要求和历史；已有计划时仍受既有跨阶段授权与失效规则约束。
- 真正当前用户义务需要不存在的控制器能力：保持未解决，使用现有 HumanIntervention 外部前提边界并附来源/问题原件，不能让作者实现控制器或自动放行。
- 建议本身没有强制效力；作者用法信息和已知缺陷仍可作事实线索。审核者不能凭个人方法偏好新增义务。

recheck_prototype 仍由现有许可执行；合法产品问题产生现有失败记录供诊断，非产品责任问题交上述责任边界。所有情况都不能代替人工原型批准。

## 缓存、暂停和兼容

当前运行使用的新自动审核必须符合新协议；旧自动通过记录不能只因旧 bool=true 复用。初次 pending、已批准重检、缓存审批检查和恢复重检均检查新依据身份。旧证据原件及自动回执归档保留；可以复用仍有效的真实浏览器观察，但必须重新独立审核。人类批准仍绑定原内容/动作，不伪造、不重复索取相同合法批准。

已完成项目不主动重开。已存在恢复请求/回答/许可/冻结模型输入不改写；新请求可携带当前阶段说明。过期自动 review 仅在正常执行入口失效，不手动迁移现场 DB。中断后已验证响应仍能幂等复用；未完成或旧协议响应不能激活。

## 验证矩阵

1. 真实 Engine 初次作者/审核、审批缓存重检、已批准原型重检都收到相同来源与有限能力；ContextPlanner 后完整材料可读。
2. 真实归档两份旧拒绝在新边界拒绝为审核响应问题，保留原件；构造有规范依据的 UI 缺陷仍回原型；正常通过仍要求浏览器与人工门禁。
3. 未知标准、候选/历史意见当标准、过期来源/候选/观察、虚构证据、漏覆盖、缺证据却批准、建议导致否决拒绝。
4. 明确原型用户要求和 unsupported capability 保持阻塞；最终 JSON/真实往返仍完整保留；不会执行候选 .mjs。
5. 无效审核纠正、暂停后恢复和成功回执复用：无产品写入、无正式问题污染、不清计数、不重复回答冻结请求。
6. 旧自动通过失效、新证据重审、同一人工批准复用、内容变化使批准失效；三入口覆盖，原 scope/源码保护反例保留。
7. 定向测试、相关扩展、静态和固定版本全量；独立审查后才恢复真实 demo5。回放不声称真实模型已经完成纠错或产品通过。

## 风险、回退与交付

新结构会让不合约审核走响应恢复，可能增加一次模型调用；必须保留校验细节避免无意义重试。语义误读无法彻底机械消除，反复争议按现有无进展策略升级，不靠减少验收过关。引用/缓存涉及共享路径，必须测试真实调用者而非仅 mock 正确输入。

按单一完整根因修复独立提交，不 push。回退源码不会删除任何运行原件；未知新版自动证据不能作为旧版验收依据。交付给出代码提交、全量源码摘要、原场景回放及独立审查记录，再按原 run 正常恢复，运行期外部修复提交数从 3 增至 4。不启动新 demo。
