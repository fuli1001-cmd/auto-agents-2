# 质量优先修复：实现与验证记录

基线：`35af1218e9115b676fcedcac045834e8926e46e5`。本记录对应用户最后确认的实施范围：修复控制器契约，在单一生产路径内去掉同次请求的重复研究正文，并清理失去消费者的诊断日志。诊断脚本证明缺陷存在，不作为修复通过证据。

## 执行与恢复契约

- 执行快照与模型材料分开。快照包含受跟踪输入、候选文件、链接及目标内容、可执行位；声明的 `Command.inputs`、Node 安装内容和实际继承的运行配置另纳入检查身份；运行变量只保存摘要，不记录凭据正文。新增输入不代表输入集合已经完备。
- `Command.inputs` 对旧记录默认 `[]`，新 provider 输出严格要求该字段。空声明保留旧验收义务键；实际输入变化改变义务键，不能伪造进展。旧证据须符合新版检查身份才能复用。
- 环境请求聚合显式入口或 root/backend/frontend/api/web 自动入口。每根优先 lock、requirements、pyproject；`-r` 与 `-c` 分别保留安装与约束语义。Conda YAML 的 pip 段与其他 pip 输入一起解析、一次安装，再执行 `pip check`。本地依赖绑定环境内源码副本。
- 就绪判断检查解释器、包文件、锁和副本的实际内容。损坏实例保留，另建实例。正常运行缓存不计入不可变安装内容；每次交付和恢复仍执行新探针。
- provider 使用独立公开源码快照和 Git 库，屏蔽原项目历史与控制器私有状态。当前秘密准入采用第四轮 `public-v5-paths`：只保护秘密路径，不扫描普通文件、提示词或已授权附件的秘密值／哈希／inode。真实秘密必须仅存于秘密文件，其余材料使用配置引用；日志脱敏独立保留。前三轮秘密别名规则已按用户指示替换，历史审计记录仍保留。
- 写入路径先规范化，整批硬错误先检查，再请求保护文件审查。拒绝符号链接写入；应用前检查类型、权限和字节前后映像。UTF-8 BOM、CRLF 和混合换行保留，replace 精确匹配，不进行整文件换行猜测。
- 调用结果在临时响应清理前持久化；成功结果、使用量和调用检查点共同提交。远端返回但尚未形成耐久本地记录的窗口仍可能重试，缺少使用量标为不完整。
- 规划、README、实现、原型、交付修复保存候选；README 和交付修复保存 prepared patch。修复轮数与新候选阶段原子更新；恢复不重复应用 replace 或重新生成已知候选。
- 原型审批绑定内容与动作；检查器版本独立。版本升级重检和重审，不把相同审批对象变成新的产品审批。集成检查重放原动作。
- 发布区分 Git 对象与检出字节。候选先规范为支持的检出形式再验收；日志记录规范对象和实际字节映像，恢复按删除叶节点、创建父节点顺序执行。自定义 filter、ident、working-tree-encoding 不在支持范围，在发布前拒绝。未知用户内容不递归清除。
- 旧交付先按旧快照和日志核对，再增加新版验证记录；已经发布的状态不因换哈希算法而直接重发。不能证明的状态停止并保留现场。轮数、停滞历史、旧证明不重置。

## 材料与质量门槛

64,000 是 prompt 与 schema 合计的**字符软目标**，不是 token 限额，不包括原生会话、工具返回和图像。8,000 是反馈展示的软目标，不是截断规则。删除累计 `max_tokens` 停止条件；旧配置字段可读但忽略，重新保存不再输出。实现轮数、停滞和基础设施重试限制保留。

当前策略已由 2026-10-18 全阶段输入方案替换：每次调用提供当前任务必需事实和可追溯的补读入口，原始事实完整保留。短必要正文内联，大正文、历史和完整目录按阶段引用；来源未明确的共享约束保守保留。模型、推理深度和原生执行权限仍取用户配置。不能为达到字符目标剪掉 schema、权限、验收条件或失败证据；证据不足不能通过门禁。

研究输入现在优先选择精确章节及必要的短链接定义，保留版本、锚点、来源和验证义务。章节索引绑定原正文；大章节和其他相关定义按需读取。请求内相同快照的正文去重继续适用，不做语义合并或跨版本合并。先前的全文内联对照只说明当时的去重行为；新的阶段选择须通过独立的输入、恢复及真实调用验证。字符数下降不能代替实际 token 计量。

完整设计目录以固定版本索引保留；排序只提示路径词匹配，不能把前 12 项称为最优候选。源码选择优先任务、证据位置、直接项目依赖和入口配置；读取选择与写入授权分别处理，原始换行保持。完整公开文件在实际挂载快照中可读，依赖诊断仍可读取完整锁文件及包含链。

材料清单记录来源地址、内容身份、用途、必要性、呈现方式、字符计量、遗漏和能力身份。`controller_readable` 不等于“原生工具已读”或“模型已理解”。Codex 不再只附前八张图片，缺失图片或附件明确失败。依赖原生工具读取的附件会先执行随机内容读取探针；间接图片读取同时验证 PNG，探针绑定 CLI 版本、二进制、有效 profile、协议与视图版本，单独计入用量。探针仅证明该能力组合能读取测试材料，不证明任务判断正确。

用户已在 2026-10-18 批准“精简首包、按需补读”和少量真实 provider 对照。历史正文引用、检查证据视图、章节索引及按角色规则装配因此纳入当前范围，细则见设计规范的“按阶段选择模型输入”。不增加默认模型摘要调用、原生会话增量依赖或生产压缩开关；旧格式仅作为手动 A/B 对照 fixture。此次验收记录与早期对照分开保存。

## 证据、日志与资源

问题台账由控制器按稳定任务 origin、确切 scope、位置和问题字段生成 ID，重复观测保留次数和证据，不做语义相似合并。只有同一范围的独立批准审查才能关闭旧问题，其他范围通过不能代替。实现反馈不再递归嵌套整轮状态，也不从日志尾部再任意截取 4,000 字符。

检查 stdout/stderr 增量解码并跨块脱敏，完整的脱敏流保存到内容寻址产物；显示尾部不替代原始证据入口。机器报告独立解析。单条诊断记录超过 1 MiB、需要完整解析的机器输出超过 32 MiB、写盘失败或采集中断明确失败，不把不完整输出标作通过。这些是当前解析能力边界，不是材料 token 优化。原生 provider 诊断仅记录分类，不记录配置正文。

临时采集文件在归档后退出作用域即清理，崩溃遗留由启动恢复处理。归档的 `check_log`、`dependency_log` 由消费者决定保留：生产中尚未提交的日志、正在读取的模型调用、未完成阶段、暂停或等待中的运行、开放问题以及显式恢复引用均受保护。成功安装必须连同后置检查完成才释放日志；安装失败保留到成功重试或不再需要。运行结束或检查点被替换后，无其他消费者的日志正文自动回收。取消不会移除开放问题或显式恢复所需日志。

回收先持久化释放记录，再删除正文；新的生产、检查点或读取会撤销待删除状态。删除失败保留现场并重试，不撤销已确认的交付。已经缺失且没有释放记录的文件仍视为异常，不补记成正常释放。历史回执不改写，模型材料明确列出已释放日志，不附虚假可读路径；若需要这些诊断须重跑相应检查。结构化结果、JUnit、审查结论、输入身份和验收依据独立保留，不能凭释放状态推进门禁。哈希、大小及释放记录作为小型元数据保留；仍有消费者的日志也保留，不承诺全部磁盘占用恒定。

原始 HTTP 响应与提取文本分别归档，记录最终 URL、请求 URL、时间、MIME、编码和提取版本；保留链接、表格分隔和锚点。相同抓取身份只请求一次，仍保留每项声明及其声称版本；成功下载不代表声明、版本或一手来源已经证实。

产物登记显式依赖边，GC 同时理解旧嵌套 JSON 引用。截图、完整日志使用内容寻址文件，复制和散列采用分块 I/O。活动阶段、恢复状态及保留的验收记录是根；解除最后引用才回收。成功交付清除候选和调用检查点。缓存清理一次计算候选大小；具有可证明不同目录前缀的 glob 任务可并行，其余冲突仍保守处理。

### 为什么修了四轮仍有问题

| 扫描 | 实际扫描文件数 | 评论条数 |
| --- | ---: | ---: |
| R1 | 98 | 89 |
| R2 | 102 | 52 |
| R3 | 104 | 35 |
| R4 | 110 | 43 |
| R5 | 116 | 37 |

这些数值不是同一批输入的剩余 bug 清单。扫描对象增加，模型每轮会发现此前漏掉的分支；R5 还跳过了设计文档、大部分测试及 `test_reports.py`，却扫描了历史 XML，所以评论本身不能当成事实或项目 bug 总量。

同时，前四轮修改确实引入了新问题，不能全部解释为“扫描越来越深入”。同一故障场景对照 R3 `86a3b6f` 和 R4 `072de83`，确认 #6、#9、#11、#12、#18、#29 共六项是 R4 回归。#13/#14 是新 verification_only 流程的衔接缺口；#22 是已有清理问题的防重复调用保护仍不完整，R4 测到了 PolicyViolation，但没有覆盖 OSError 的外层转换。#23 的消息列表和 #28 的 LIKE 前缀来自更早代码。#8 是早期引入锁重放后没有覆盖完整发布边界。不能把这些不同来源合称“全是全新问题”或“全是旧问题没修好”。

生产 Python 代码从首轮前 45 个文件、9,202 行增长到 R4 后 53 个文件、11,728 行，约增加 27.5%。四轮分别修改 33、27、29、31 个生产文件；新增/删除行分别为 1,274/578、733/186、871/198、998/388。修复引入了恢复、保护、归档等新机制，新状态组合也增加了。局部分支通过不等于完整生命周期正确；尤其“提交成功后清理失败”“中断发生在两次持久化之间”“一个清理失败后还有另一个资源”是此前覆盖不足的组合。我对前几轮修复和测试覆盖不足承担责任。

OCR 能帮助找到真实缺陷，但“扫描—修复—再扫描”不能单独证明净 bug 数下降，更不能承诺评论最终收敛到零。本轮因此按行为矩阵测试正常、失败、取消、重启和资源回收；用稳定条目记录根因、前后证据和重复项。后续应按较小子系统批次修复，关注确认关闭数、同根因复发数、修复引入的回归数及真实交付成功率，而非只追逐下一次扫描条数。

附件限制的发生概率目前无法可靠估计：现存样本只找到 3 个截图引用（最大 33,983 字节）和 2 个旧测试附件引用（最大 5,125 字节），不包含有代表性的长录像。64/256 MiB/256 个是可配置的初始保护值，不是根据这些样本推导出的可靠分位数。超限时等待用户调整、保留现场和不截断证据，是已确认的产品选择。

本轮真实 Next.js 16.4.0 交付验证还发现一项报告之外的兼容问题：首次请求新增 `.next/server/route-cache`，导致原来只排除 `.next/cache` 和 trace 的产物摘要误报变化。前后比较确认源码、依赖和运行变量摘要一致，差异仅为该缓存目录内的六个文件。[Next.js 16.4.0 的文件系统缓存实现](https://raw.githubusercontent.com/vercel/next.js/v16.4.0/packages/next/src/server/lib/incremental-cache/file-system-cache.ts) 区分这部分请求缓存与构建种子。本轮仅增加这个明确目录的运行缓存豁免，服务代码和构建清单仍校验；新增反例测试证明修改 `server/app/page.js` 会改变产物身份。两次失败的烟雾现场保留，修复后重新运行完整交付验证；这项额外发现不计入 R5 原有 37 条评论。
