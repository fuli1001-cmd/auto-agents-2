# 阶段职责回送与派生计划合同纠错

状态：2026-10-22，用户已批准本方案范围；本文先于实现落盘。

## 1. 已确认的问题与目标

demo3 的原用户需求没有指定 Node/npm 补丁版本。设计阶段把具体版本选择交给计划阶段；计划选择 Node 22.23.4/npm 10.9.9，实际环境为 22.23.2/10.9.8。第一次修订加入版本一致性检查，第二次修订声明 environment.yml，实际 Conda 创建返回 `ResolvePackageNotFound: conda-forge::nodejs==22.23.4`。这只证明该次指定渠道和约束解析失败，不证明任何渠道都不存在该版本。

第三份修订提案依据这一真实失败调整技术版本及检查表达，`plan_revision._retain_checks` 在独立审核前以命令字面变化拒绝。检查数量相同本身不能证明该提案正确，但当前程序也没有让有依据的错误派生检查接受正式语义审查的通道。时序纠错只允许移动验收条款的阶段，不允许修正命令，无法解决本次问题。

现有阶段恢复已有许可、历史归档、版本和失效机制；缺口是这些入口没有共同的责任/产物声明与可核验纠错请求。目标是统一这些入口的控制面，同时补齐计划作者自己的纠错闭环。不是让实现代理自行改计划，也不是让环境安装器改断言。

## 2. 已核验的入口及处理器

| 入口 | 现有路径 | 本轮处理 |
| --- | --- | --- |
| 模型诊断选择上游阶段 | RecoveryController.resume → RecoveryPolicy.authorize → _resume_replan | 许可之后构造并校验共同纠错请求；保留原权限决定 |
| 控制器发现阶段合同错误 | Engine._controller_replan → _grant_replan → _resume_replan | 同一职责表和请求；有已接受计划时仍必须转 PlanPatch |
| 旧持久 replan 恢复 | Engine 启动适配及 _resume_replan | 保留旧请求、答复与许可；只补控制器元数据，不重新解释授权 |
| 局部计划修订 | RecoveryController._patch → 独立 review → Store.activate_plan_patch | 绑定旧计划、原始需求、失败证据、映射、审查和候选；事务激活 |
| 原型、设计、任务、说明、交付修复文件提案 | PatchRepairService.prepare 及 prepared 重放 | 统一产物所有权校验，原有路径/敏感/保护审查继续执行 |
| 环境、检查、审核 | EnvironmentManager / Verifier / readonly review | 保持实际执行与只读职责；不赋予修改业务合同权限 |

现有粗粒度重入目标是 clarify/provider_research/prototype/design/readme；plan 有已批准版本时走局部修订。develop 的修复、复验和最终审核沿用现有恢复动作。没有任意阶段间跳转，也不新增每阶段的精细修订系统。

## 3. 固定职责与产物所有权

新增一个小的公共模块声明有限动作到责任阶段、处理器及产物的映射。该表同时用于请求构造、控制器校验和各角色提示；提示文本不构成权限。

| 责任方 | 能提出的内容 | 不能做的事 |
| --- | --- | --- |
| clarify | 原需求的结构化澄清、覆盖分析 | 改写原始用户输入或替用户决定新目标 |
| provider_research | 可核验研究材料 | 把建议当安装成功或扩大需求 |
| prototype | design/prototypes 与 DESIGN.md | 改架构、计划、实现或替代原型批准 |
| design | docs/aa2/design.md、design-*.md、design/ 下架构 Markdown | 改用户需求或直接实现产品 |
| plan | 结构化任务、范围、依赖、检查及其派生文档 | 自批候选、清零计数、改变原用户约束 |
| develop | 已接受任务/交付修复范围内源码、清单与测试提案 | 改需求、原型、架构或计划文件 |
| readme | README.md、普通 docs、.env.example | 改受其它阶段拥有的文档或源码 |
| environment/checks/review/deliver | 分别安装取证、执行取证、只读判定、既有发布流程 | 修改业务要求、私造证据或另增权限 |

交付中的原型修复虽复用 implement 模型，产物所有者仍由控制器明确设为 prototype；不能根据模型输出推断特权。prepared 补丁在恢复应用时仍校验所有权，不能绕过。源路径规范化、符号链接、敏感文件过滤和原有 scopes 继续由 workspace 验证；所有权检查只收紧，不扩大读写范围。

## 4. 共同纠错请求与许可

纠错请求由控制器从已记录失败/待重入请求和已选动作生成，包含：版本、责任方、固定处理器、触发证据引用和原因、旧计划版本及哈希、各阶段已接受产物哈希、原始需求身份、现有许可/旧授权关联、保留义务和失效范围。计划修订还携带逐项条款映射；其它阶段沿用已有重入请求及旧产物归档。

共同校验拒绝错误责任方、未知动作、过期旧版本/来源、与许可动作不符，以及把已有计划整体清空来回避 PlanPatch。原始 capture、旧需求、旧计划和计数不能被请求更新。模型的 action 是建议，不是许可；原有 RecoveryPolicy 仍决定动作能否执行。

既有待答问题及绑定不迁移、不替换。旧许可仍按原规则校验，获得许可之后才补充请求元数据。旧 prepared/activated journal 不强行转成新格式；新纠错 journal 必须完整校验，不能利用缺字段走旧格式。已激活版本幂等返回，未激活的旧版本漂移拒绝。

## 5. 正式派生合同纠错

PlanPatch 新增显式 `contract_corrections`，与已有 timing_corrections 分开且不可混用。不是自动重写旧命令。固定目标类型限于任务 acceptance、任务 checks、final_checks、runtime_prepare、runtime_probes；每项有 task_id（适用时）、零起始索引、完整旧值/新值、错误派生决定的说明、实际证据引用、必须保留的实质义务。命令使用完整 Command 值，旧内联检查与普通命令用相同方式处理。

机械检查：

- base_revision、failure_ids、旧条款/命令必须精确匹配；重复、漏映射、多余映射拒绝。
- 不增删/重命名任务，不改来源、需求 ID 或依赖关系；原验收和检查按原位置保留，只有显式映射可以变化。
- 检查 cwd、最低 expected_tests、已有输入与输出保护；对应命令必须存在。数量相同不构成通过。
- 任务路径不能删除；必要新增路径必须为原已批准检查声明的明确输入路径，仍通过阶段所有权与正常计划范围校验。禁止借纠错引入新通配范围。
- 未映射最终合同、准备命令和探针保持原值；描述/文档和必要实现路径的变化交独立审核确认与本次纠错的关系。
- 环境清单选择、原型等其它合同变化不混入此模式；另走已有正式修订。

独立审查对每个映射显式判断：是否确属模型派生的技术决定、原用户约束未改、业务断言与历史义务保留、测试选择/收集未削弱、依赖与路径范围最小、旧新条款无矛盾。审查读取原始 capture/澄清/设计、旧计划、真实失败与完整候选，引用这些独立来源；作者自称等价无效。任何否定、未知、缺少来源或映射不完整均拒绝。审查并不能数学证明任意程序语义等价，剩余风险由实际复验和最终独立审核控制。

新 journal 绑定责任请求、旧计划、完整 patch、候选、独立 verdict、原需求和控制器合同。激活事务内重算结构变化、审查覆盖及全部绑定；只允许经过审查的候选。之后重新实现或复验；计划获批不等于包已安装。

## 6. 失效、历史和无进展

计划局部变化复用旧/新依赖图的 descendants：相关任务旧验收失效，修改实现合同的任务 needs_repair，其余按既有规则 reverify；环境/最终合同变化保守复验全部任务。保留用户文件、历史候选、未应用提案身份、原 origin、累计次数、失败和审批。

跨阶段重入继续用 Store.complete_replan 的现有下游后缀失效与工作树归档；请求和旧需求/计划随 replan_feedback 明确传给重入作者及审核者，不能把空上下文重新写计划当纠错。首次范围不增加精细依赖图。恢复中断继续同一个请求/候选/审查，不制造新额度。

相同实质证据下的合同修订拒绝纳入现有两次无进展路径排除；保留记录，不因改措辞、换调用或再许可重置。真正新来源、计划、失败观测或控制器能力版本可改变可执行条件。其它阶段沿用既有重入进展判定；不承诺任意语义循环都能机械检测，也不新增模型总时限。

## 7. 验证与验收

1. 用真实 demo3 归档复现旧 _retain_checks 拒绝；在隔离副本构造完整新映射并验证结构可进入独立审查。不能直接把历史被拒提案激活到实际 run。
2. 真实 RecoveryController/Engine 测试覆盖生成→机械校验→独立拒绝/批准→原子激活→受影响失效→恢复复验；覆盖计划与粗重入入口、普通范围写入与 prepared 恢复。
3. 反例：改原用户版本要求、删除业务断言/测试选择（语义拒绝）、最低测试数降低、输入/输出移除、旧值不符、错责任方、通配路径扩大、未审/缺映射/篡改 journal、过期版本、重复激活、审查中断、计数保留、相同证据无进展。
4. 保留已有时序修订、普通 PlanPatch、旧 journal/许可/问题、原型授权、敏感过滤和历史提案非事实测试。
5. 运行相关静态和定向/扩展测试，再跑完整套件；源码摘要绑定最后被测版本。通过后独立本地提交、不 push。
6. 正常恢复同一 demo3 run，依据既有用户授权答原恢复请求，让 aa2 重新提出正式修订，审核、激活、安装与测试；验证业务检查与最终交付。真实运行失败继续保存证据定位，不外部代写产品。

## 8. 非目标与回退

不实现通用规则语言、任意自然语言证明、动态权限平台、所有阶段局部补丁、精细全图失效、审计保留或缓存迁移。不修改已交付 demo/demo2，不改变内部模型、网络安全或许可机制。

若验证失败，原 demo3 维持正常 PAUSED/原问题未答，保留全部现场。提交后可回退源码，但新格式未激活纠错 journal 不得由旧程序猜测执行，应保留并用支持该版本的控制器恢复；已激活计划仍为普通 PlanResult，正常证据门禁不变。


## 9. 实现记录与上线前验证

公共职责模块为 `stage_responsibilities.py`，显式映射/语义审查模块为 `contract_corrections.py`。既有 stage-reentry、PlanPatch 和文件提案入口均调用公共职责校验。控制器构造的请求只关联旧许可，不产生许可；恢复分派已经完成的许可只作为来源保留，不能再次覆盖其完成结果。

首次计划作者重试没有已接受计划，统一路由明确标为 stage_reentry；有已接受计划时禁止整体 plan reset。新 contract journal 使用 version 2，不能删除映射后退回旧校验。旧 version 1 普通/时序 journal 继续原校验。仅验证模式沿用现有真实覆盖检查，其新 journal 额外绑定检查摘要；激活时核对同一结果、源码及通过状态，不能凭布尔声明放行。

真实 demo3 回放保留旧 proposal 的原始拒绝；隔离场景映射 task acceptance[0]、acceptance[8] 和 checks[0]，原 6 检查及最低用例 `[0,0,0,0,4,0]` 保留，其余业务条款、TASK-002、最终检查和预览合同不变。完整 RecoveryController 的提案、独立审查调用、激活和失效路径已运行；审核使用确定性测试替身，不声称已批准实际 demo3 或已证明任意语义等价。实际运行仍须重新生成正式修订、真实独立审核和完整复验。

截至启动全量前：新增 58 项边界测试通过；真实工作流/恢复等扩展 268 项通过；补充仅验证模式与恢复工具 73 项通过（这些集合有重叠，不能相加当测试总数）。静态 ruff 和 git diff --check 通过。完整套件结果和源码身份由任务目录中的 stage-correction-full-* 文件记录。

未验证边界：模型能否在实际新 prompt 下正确生成映射、语义审查是否正确、目标包渠道是否可安装，均需 demo3 后续运行证明；本实现不保证任意自然语言计划错误都可机械识别。其它阶段仍为现有保守重入，不提供任意细粒度产物图或全部循环识别。


### 全量集成回归与绑定职责修正

首轮全量发现五项失败，归为三处兼容问题：材料探测和 provider 连通性探测应保持专用诊断提示，不继承业务流程职责；越界提案仍须保持既有 `Out-of-scope` 异常分类文本；原型复验在已发布新自动证据后中断，公共纠错绑定不能把本动作负责更新的结果当作冻结输入。

最后一项修正只针对 `prototype_recheck`：公共绑定保留原需求、原型文档、设计、计划、版本及许可；许可摘要同时绑定已有 `prototype_binding` / `preview_binding`。原型复验既有处理器每次恢复仍校验真实源码、原型内容与动作、人工同意、计划及发布状态，并严格比对日志中的浏览器报告和独立审查结果。该动作更新的完整 `prototype_approval` 不再重复作为公共冻结输入；其他动作仍冻结完整批准记录。不增加授权，不接受仅凭模型声明的证据替换。

补充发布后源码变更、人工同意失效、计划变更、审核证据损坏及许可替换的反例，并验证其他纠错动作仍拒绝批准记录变化。原有四个中断边界测试保留。首轮失败原件保存在任务目录 `stage-correction-full-*`，修正后的完整验证使用 `stage-correction-final-full-*`，不能把首轮计为通过。

最终新增边界共 64 项通过；此前集成组合 128 项中的 127 项通过，唯一失败为新增许可漂移反例读取夹具位置错误，修正后由上述 64 项完整复验覆盖。首轮原有五项失败均已消除。最终真实归档回放通过，保留原拒绝、全部未映射条款及累计次数。第二轮全量收集 2,032 项，结果以源码绑定的 `stage-correction-final-full-*` 为准。


## 10. 真实激活中的角色引用上下文修复

2026-10-22 的真实 demo3 候选与独立审查均通过前置校验，但 version 2 prepared journal 激活失败。复现定位到 `RecoveryController._patch` 只冻结九个审核根字段，`validate_contract_journal` 却将该子集同时当作作者与审核的输入。作者引用的 `plan` 是旧批准计划，审核中的 `plan` 和 `patch` 是未激活提案；`recovery_decision`、阶段合同及其他真实调用输入也可能被截掉。先前工作流回归只引用共有来源，因此未覆盖此次交接差异。

最小修复：

- 新 contract journal 使用 version 3，分别保存完整 `contract_author_context` 和 `contract_review_context`，审查绑定摘要覆盖两者。它们是控制器已经提供的只读输入，仅存在恢复日志中，不额外加入模型提示词。
- 激活按原角色重新执行引用规则，作者的旧计划与审核的候选不能混用。审核候选和补丁保持 proposal 权威，不能替代旧计划、原需求或真实失败。原需求/澄清/责任请求仍绑定现场，公共来源一致、阶段合同有效；完整旧新条款、独立语义结论、覆盖检查及失效规则不变。
- 旧 version 2 prepared 只做有证据的兼容读取，不重写旧日志，不重新收费或重新生成候选。缺失根字段必须来自同一 operation 已冻结的 recovery context、成功 invocation 回执及内容寻址的原始展示记录；逐根比对原始内容哈希或未经改写的内联值。引用仍按相应角色校验。材料缺失、内容漂移、回执不一致或无法恢复的来源拒绝，不能猜测当前工作区来补证。version 1 普通/时序修订保持原流程。
- Store 在同一激活事务内完成兼容材料读取与复核，再执行原子 CAS；已激活版本继续幂等返回。完整性失败不改变旧计划、计数或 prepared 状态。

验证覆盖真实 RecoveryController 生成、独立审核、prepared 中断恢复、重复激活和保留计数；新增引用覆盖旧计划、候选提案、恢复决定、阶段协议、历史材料、任务来源、保留候选、工程视图和受影响集合。反例包括未知引用、提案冒充事实、角色交换、篡改/丢失上下文、过期输入与协议、缺失/损坏旧归档。真实 demo3 的原候选、原审核和原展示归档在隔离数据库完整回放，四个映射通过并只激活一次，原数据库保持暂停且摘要不变。

边界：旧格式未保存且无法从真实归档证明的其他来源仍需正式调和，不能把本次可恢复推广为所有旧记录可恢复；模型语义审核的正确性与实际环境安装、业务验收仍须运行验证。此修复不新增一般证据框架，不改变审核权力、访问权限、测试门槛或模型设置。
