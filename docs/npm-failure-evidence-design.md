# npm 安装失败的诊断证据交接

## 现场与根因

2026-10-23，demo4 第二次安装失败后，decision 原生会话以 `server_overloaded` / `Selected model is at capacity` 结束，无模型结论；这是外部容量失败，不是 JSON 解析错误，不修改 provider 重试或模型配置。

独立诊断确实只得到 `environment_error` 短文本。`EnvironmentManager._command` 已归档 stdout/stderr，但 `DependencyResolutionError` 只保留字符串，`WorkflowEngine._task` 和 `_task_failure` 继续丢掉原件引用。npm 更完整的 debug 日志存在于共享下载缓存，未进入上述归档；其正文包含实际 Node 22.23.4/npm 10.9.9、Arborist 堆栈和未完成的依赖求解记录。由于安装未完成，不存在可声称完整的已安装依赖图。原诊断转而处理已有 S07 测试审查意见，明确承认不能解决安装故障。

此前 2e7ad6e 解决错误分类，使故障能进入恢复；本修复补齐该路径缺少的诊断输入。不是新建通用采集系统，不给诊断直接安装或修改产品的权限。

## 最小方案

1. 类型化依赖解析异常携带可选、版本化的失败证据：实际命令、退出码、完整 stdout/stderr 的不可变引用。Conda 包装异常保留相同字段；旧构造调用仍有效。
2. npm 的两条正式命令（首次锁解析、`npm ci`）统一使用一个窄包装。每次命令分配独立受控日志目录，通过官方 `npm_config_logs_dir` 指定，不读取 stderr 声称的任意路径，也不读取共享缓存中的旧日志。不改 `logs-max`、代理、TLS、依赖选择或重试规则。
3. 失败后、沙箱子进程退出后，安全读取该命令目录内普通 debug 日志，先过滤已有秘密值和 npm 凭据表达，再归档为现有 `dependency_log`。符号链接、非普通文件、超限、无日志均记录具体不可用状态；不截断后冒称完整。只读目录描述符避免跟随路径替换。沿用现有日志租约/不可变哈希机制，原始受控临时材料由现有资源规则保留/回收。
4. Engine 把证据写入当次失败候选和 FailureRecord，绑定任务源码身份；诊断、决策、修复候选及基线重入使用同一事实。ProviderRouter 沿已有引用索引挂载只读正文，不挂载整个缓存或原运行时。
5. 新日志只证明失败命令观察，不证明安装成功、完整求解图或修复权限。缺失旧记录不回填伪历史；旧请求、冻结输入、已答批准和计数不迁移重写。旧记录需要新材料时，经正常已授权恢复选择一次环境重检，产生新失败观察后再诊断。

## 验证

- 新回归在旧代码失败：失败异常没有证据、npm debug 不可读、真实 Engine 诊断/修复上下文缺原件。
- 两种安装入口，缓存开/关；Conda 相同异常包装；无日志、日志关闭、软链接/非普通文件、超限和敏感内容反例。
- 真实 Engine 故障→诊断→许可→修复（含中断续跑）验证引用和历史保留；ProviderRouter 真正派发夹具验证正文可读/不可写、损坏引用拒绝。
- 用 demo4 真实 debug 归档作隔离回放，不编辑 demo4 产品或原数据库。可用小型离线真实 npm 命令验证日志目录协议，不重新安装历史 demo。
- 定向、相关回归、完整 pytest，Ruff 与 diff 检查；源码摘要绑定结果后独立 Git 提交、不 push。

## 边界与恢复

不承诺 npm 依赖修复已完成；依赖候选仍由 aa2 提出、保护审核、真实安装和原检查验证。决策容量故障保留既有人工 fallback；原 question_447dc1965a364505 正常批准只覆盖展示的一轮恢复。测试或输入绑定不一致则停止提交/恢复，保留证据。无新增总超时、无清缓存、无用户配置/安全设置变更。

参考：[npm v10 logging](https://docs.npmjs.com/cli/v10/using-npm/logging/)、[npm logs-dir](https://docs.npmjs.com/cli/v10/using-npm/config/#logs-dir)。
